# Repository Guidelines

## Project Purpose

`brrr` is a small, portfolio-ready market-data and trading-strategy research
application. It imports historical OHLCV candles, lets authenticated users
inspect assets and price history, runs reproducible long-only backtests, and
compares strategies with buy-and-hold.

Keep the application focused and complete. It is not a broker, exchange,
real-time trading system, social network, or production quantitative platform.
Do not add order execution, payments, subscriptions, AI features, leverage,
short selling, options, notifications, or speculative architecture.

## Source-of-Truth Boundaries

- `/Users/maciejraaa/workspace/brrr-api` is the read-only domain reference.
- Never edit, delete, reset, or commit files in `brrr-api`.
- Preserve the behavior in the current Prisma schema, market-data code,

- Do not restore concepts that exist only in obsolete NestJS migrations, such
  as COT or analysis snapshots.
- Translate domain behavior into idiomatic Rails; do not reproduce NestJS
  class structure or introduce repository/service layers around Active Record.

## Technology and Architecture

- Ruby 4.0.6 and Rails 8.1.3.1.
- PostgreSQL with database constraints, foreign keys, and `timestamptz`.
- Sidekiq through Active Job, backed by Redis.
- Server-rendered ERB views with Turbo, Importmap, and small Stimulus
  controllers where interaction benefits from JavaScript.
- Tailwind CSS through `tailwindcss-rails`.
- Rails-native authentication generated by `bin/rails generate authentication`.
- Rails-native Minitest, with WebMock for provider HTTP tests.
- TradingView Lightweight Charts may be imported for candlestick and equity
  charts; do not introduce React or another frontend framework.

Prefer conventional Rails organization:

- Active Record models own associations, validations, scopes, and compact
  persistence invariants.
- RESTful controllers remain small and always scope user-owned data through
  `Current.user`.
- Plain Ruby objects under clear domain namespaces own provider adapters,
  indicators, strategies, and the database-independent backtest engine.
- Active Job classes coordinate asynchronous work and persistence.
- Use partials for repeated UI and helpers only for presentation logic.
- Maintain concise, single-responsibility methods (preferring methods <= 20-25 lines). Extract complex orchestration, database transactions, and data mapping into focused, well-named private helper methods.
- Do not create a generic `ApplicationService`, repository abstraction, or a
  `lib` dumping ground.

## Correctness-Critical Rules

### UTC and market data

- Rails, Active Record, and every PostgreSQL session must operate in UTC.
- Candle `open_time` is a UTC instant. A daily candle opens at `00:00:00Z`; it
  is not a calendar-date column.
- Date-only upper bounds include the entire requested UTC day.
- Persist only completed candles. Capture one `as_of` instant for an entire
  import and use it for every asset and interval.
- Overlap and restate the latest five stored bars on repeat imports.
- Validate timestamp ordering/alignment, interval duration, coherent positive
  OHLC, non-negative volume, and duplicate conflicts before writing.
- Upsert idempotently using the database key `(asset_id, interval, open_time)`.
- Never store prices or volume in binary floating-point columns. Use exact
  PostgreSQL numeric values and `BigDecimal` at persistence boundaries.
- Isolate expected provider/configuration failures by asset. Database and other
  infrastructure failures must abort the job rather than look like partial
  provider success.
- Tests must cover DST-adjacent instants and a non-UTC process time zone.

### Provider behavior

- Yahoo Finance is daily-only and uses explicit timestamp bounds. Its endpoint
  is unofficial and must remain isolated behind a small provider contract.
- Binance supports hourly and daily candles and paginates forward with a
  bounded request count and an advancing cursor.
- Retry only transient network, rate-limit, and server failures with bounded
  exponential backoff and an explicit HTTP timeout.
- Respect reasonable `Retry-After` values, but fail instead of holding a worker
  through an excessive provider ban.
- Provider and provider-symbol fields must be both present or both absent.
- Do not change an asset's configured provider after bars exist unless an
  explicit safe replacement workflow is implemented.

### Backtesting and financial logic

- Keep the engine independent of Rails and database access.
- Signals calculated from bar `i` fill at bar `i + 1` open. Never introduce
  look-ahead through controller, job, strategy, or query behavior.
- Target weights are constrained to `[0, 1]`; no leverage, shorting, negative
  cash, or implicit margin.
- Charge fees and slippage on every fill and skip rebalances at or below 0.5%
  of equity.
- Trade returns come from actual net cash flows, including partial rebalances
  and costs.
- Mark a final open position to market with closing costs, and exclude it from
  realized win rate.
- Validate finite positive prices, increasing timestamps, matching input
  lengths, positive capital/annualization, and valid costs.
- Calculate metrics from the full equity curve. A bounded/downsampled curve may
  be persisted for display only.
- Run buy-and-hold over the same window and costs and persist its benchmark
  metrics.
- Persist exact resolved strategy parameters. Reject unknown strategies,
  unknown parameter keys, non-finite values, and invalid relationships.

## Security and Data Ownership

- Use the generated Rails authentication/session flow and CSRF protection.
- Scope every backtest query and mutation through `Current.user.backtest_runs`.
- Never expose another user's records through an unscoped ID lookup.
- Whitelist registry keys and parameter keys; never constantize user input.
- Do not expose raw exceptions, stack traces, provider internals, credentials,
  Redis URLs, or database URLs in user-visible errors.
- Keep `config/master.key`, `.env`, databases, logs, generated assets, and local
  runtime data out of Git.
- Seeds must be deterministic and offline. Clearly distinguish demo data from
  provider-imported data so a real import cannot silently mix fabricated and
  live series.

## Development Commands

```bash
bundle install
bin/rails db:prepare
bin/dev
bin/rails test
bin/rails test:system
bin/rails tailwindcss:build
bin/rails zeitwerk:check
bin/rubocop
bin/brakeman --no-pager
bin/bundler-audit
```

`bin/dev` runs Rails, the Tailwind watcher, and Sidekiq. PostgreSQL and Redis
must already be running. Development and test databases are
`brrr_ror_development` and `brrr_ror_test`; never point destructive test setup
at a non-test database or at the NestJS project's `brrr_test` database.

Unit tests must not contact external providers or require Redis. Stub HTTP
calls with WebMock and use the Active Job test adapter where appropriate.

## Verification Expectations

- Start with focused tests for the code being changed.
- Before each implementation commit, run relevant tests, `git diff --check`,
  and an appropriate lint or eager-load check.
- Before final delivery, run the complete test suite, system tests, RuboCop,
  Brakeman, Bundler Audit, eager-load checks, migrations, and a production
  Tailwind/assets build.
- Treat authentication/authorization regressions, UTC errors, look-ahead,
  precision loss, non-idempotent imports, failing checks, and missing database
  constraints as blockers.

## Git and Agent Workflow

- Inspect `git status` before work. Preserve unrelated user changes.
- Do not use destructive Git commands or rewrite history.
- Do not commit unless the user has explicitly authorized commits for the
  current task. When authorized, make small, coherent, buildable commits with
  imperative messages.
- Never commit secrets, generated build output, local databases, logs, or
  temporary research files.
- Agents must stay within their assigned scope, must not spawn other agents,
  and must report the files changed and focused verification performed.
- Do not silently omit a requested behavior. If scope forces an omission,
  document the exact decision and reason.
